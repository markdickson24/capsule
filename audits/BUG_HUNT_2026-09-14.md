## Landed fixes

### 1. `capsule_member_removal_tombstone` aborts capsule and account deletion (critical)

Commit `978cd28`. Files: `supabase/migrations/20260914120000_fix_tombstone_trigger_cascade_delete.sql` (new), `src/lib/tombstoneTriggerCascadeDelete.test.ts` (new).

**Bug.** `trg_capsule_member_removal_tombstone` (`supabase/migrations/20260802120000_security_authz_fixes.sql:187-216`) is a plain `AFTER DELETE ... FOR EACH ROW` trigger with no WHEN clause, so it also fires on `capsule_members` rows removed by FK CASCADE when the parent `capsules` row is deleted (`supabase-schema.sql:34`). For any member row other than the deleter's, it inserts into `capsule_member_revocations(capsule_id, ...)`, whose own FK to `capsules(id)` (`20260802120000:47`) is immediate. The parent row is already gone from the FK snapshot mid-cascade, so the insert raises `23503` and rolls back the whole DELETE.

Reachable from `delete_capsule_with_storage` (`20260726231008:48`) for any capsule with at least one other member row, and from `delete_my_account` (`20260726231047`) for a sole-owned capsule with a still-pending invitee. Both client call sites remove storage blobs *before* calling the RPC, so the failure mode was "Couldn't delete — try again" with the media already gone.

**Fix.** New migration does `create or replace function capsule_member_removal_tombstone()` adding `if not exists (select 1 from capsules where id = old.capsule_id) then return old; end if;` before the tombstone insert. Direct (non-cascade) member removals still write their tombstone.

**Test.** `src/lib/tombstoneTriggerCascadeDelete.test.ts` boots a throwaway local Postgres 18 cluster, loads the trigger/table SQL verbatim out of the migration files, and asserts the owner's capsule DELETE succeeds, plus a control that a direct removal still produces a revocation row. Reviewer independently confirmed it fails with the exact `23503` against the tree with the fix migration removed.

**Reviewer notes (non-blocking).** The test hard-fails if no `initdb` is on PATH, so `npm test` now requires a local Postgres (present at `/Library/PostgreSQL/18/bin` here). A sibling instance of the same class exists on `capsule_members.user_id -> users(id) on delete cascade` for admin-initiated user deletes where `auth.uid()` is null; not reachable from app code, not fixed.

### 2. `capsules` UPDATE policy lets an owner rebrand `group_id` or force-unlock via `status` (high, security)

Commit `b3b0967`. Files: `supabase/migrations/20260915120000_capsules_update_column_grants.sql` (new), `src/lib/capsulesUpdateColumnGrants.test.ts` (new).

**Bug.** `"Owners can update their capsules"` (`supabase/migrations/20260515232500_capture_capsule_rls_and_helpers.sql:61-63`) is `for update using (auth.uid() = owner_id)` with no WITH CHECK and table-wide UPDATE granted to `authenticated`. Postgres reuses USING as the implicit WITH CHECK, so only `owner_id` is constrained post-write. An owner could PATCH `group_id` to any group's UUID (bypassing `create_capsule_with_owner`'s `GROUP_MEMBERSHIP_REQUIRED` check at `20260802120000:291-297`) or PATCH `status='unlocked'` (bypassing the free-tier active-capsule cap at `:279-283` and surprise mode). `owner_id` reassignment specifically was verified NOT exploitable.

**Fix.** Mirrors the established column-grant pattern from `20260722120000_audit_rls_hardening.sql` (`capsule_members`, `media`): revoke table-wide UPDATE on `capsules` from `authenticated`/`anon`, grant back UPDATE only on the eight columns `EditCapsuleScreen.tsx:127-138` (the sole client UPDATE call site) writes. All server-side writers of the other columns are `security definer` RPCs or service-role edge functions and are unaffected.

**Test.** Same throwaway-Postgres shape as #1; runs as `SET ROLE authenticated` and asserts `group_id` / `status` UPDATEs are rejected with a column-privilege error while a `title` UPDATE still succeeds. Reviewer confirmed it fails (both attacks succeed) with the migration removed.

**Reviewer notes.** Protection now lives entirely in the privilege layer; the policy still has no explicit WITH CHECK, so a future broad `grant update on capsules to authenticated` silently reopens this. `CLAUDE.md`'s "column-grant-scoped" sentence should now also name `capsules`.

### 3. Realtime `capsules` UPDATE wipes the owner-tier embed (high)

Commit `c0fe054`. Files: `src/screens/app/CapsuleDetailScreen.tsx`, `src/lib/mergeCapsuleUpdate.ts` (new), `src/lib/mergeCapsuleUpdate.test.ts` (new).

**Bug.** `applyCapsule()` did a wholesale `setCapsule(fresh)`. The `postgres_changes` UPDATE handler passes `payload.new`, the bare table row, which cannot carry the `owner:users!capsules_owner_id_fkey(subscription_tier)` embed that only `load()`'s select fetches. `ownerTier` is recomputed from `capsule.owner` on every render and gates the photo cap, member cap, export gate and owner ProBadge, so any realtime UPDATE (title edit, unlock, live-activity toggle) silently dropped a Pro owner to free limits until the next `load()`.

**Fix.** `applyCapsule` now calls `setCapsule(prev => mergeCapsuleUpdate(prev, fresh))`, where `mergeCapsuleUpdate` returns `{ ...fresh, owner: fresh.owner ?? prev?.owner ?? null }`. A fresh row that carries a real embed still wins.

**Test.** `src/lib/mergeCapsuleUpdate.test.ts` asserts a bare realtime row preserves the prior `'pro'` tier and that a row with a real embed overrides it. Fails with `undefined !== 'pro'` against the old `return fresh` behavior.

**Reviewer notes.** `mergeCapsuleUpdate.ts:3-4` cites a "Tier 2 convention in CLAUDE.md" that did not exist at the time; the convention is now documented in CLAUDE.md's Commands section by this report's commit.

### 4. Load-failure banner never clears (high)

Commit `1209bdb`. Files: `src/screens/app/CapsuleDetailScreen.tsx` (+1 line), `src/screens/app/__tests__/CapsuleDetailScreen.errorClear.test.tsx` (new).

**Bug.** `load()` sets `error = 'Failed to load capsule.'` on a failed capsule fetch and nothing in the main component ever set it back to `''`. The render gate `if (error || !capsule)` therefore showed the dead-end error page for the life of the mount, even after a subsequent `load()` (AppState `active` refetch, unlock-poll `tick()`) succeeded and populated `capsule`.

**Fix.** `setError('')` in `load()`'s success branch, immediately before `applyCapsule(...)`.

**Test.** Jest component test mounts the real screen with a supabase mock that fails the first `capsules` select and succeeds after, fires the captured AppState `active` listener, and asserts the banner is gone and the capsule title renders. Reviewer reproduced red-before / green-after in a detached worktree.

**Reviewer notes.** `cache.set('capsule:<id>', { capsule: null, ... })` still runs on a failed load (brief "Capsule not found." flash on reopen) — separate, unfixed. This is the only jest test tracked in git; its harness is not (see Harness).

### 5. `MediaGalleryModal.getItemLayout` offset is wrong from row 1 onward (medium)

Commit `59ddbea`. Files: `src/lib/galleryLayout.ts` (new), `src/lib/galleryLayout.test.ts` (new), `src/screens/app/CapsuleDetailScreen.tsx`.

**Bug.** For a `numColumns={3}` FlatList, VirtualizedList passes a row-space index to `getItemLayout` (`FlatList.js:548` returns `Math.ceil(data.length / numColumns)`), but the screen computed `offset: thumbSize * Math.floor(index / 3)` and omitted the 2px `ItemSeparatorComponent`. Rows 0–2 all collapsed to offset 0; deeper rows were ~3x too small. Taps were unaffected (renderItem's index is separately remapped); this is purely a scroll-position/estimate defect.

**Fix.** Pure `galleryItemLayout(thumbSize, index, rowGap = 2)` in `src/lib/galleryLayout.ts` returning `{ length: thumbSize + rowGap, offset: (thumbSize + rowGap) * index, index }`; the screen delegates to it.

**Test.** node:assert script with literal expectations; reviewer verified it fails against both the original formula and a half-fixed variant.

**Reviewer notes.** `GALLERY_ROW_GAP = 2` duplicates the literal `2` at the `ItemSeparatorComponent` with no drift guard.

### 6. Gallery-to-viewer taps never present the full-screen photo (high)

`src/screens/app/CapsuleDetailScreen.tsx:1329` (gallery `<Modal>`, non-transparent), `:1354` (`onPress={() => onSelect(index)}`), `:2882-2900` (both modals mounted as siblings).

**Bug.** Tapping a thumbnail inside `MediaGalleryModal` only sets `activeMediaIndex`; it never closes the gallery. `MediaViewerModal` then mounts as a second sibling `<Modal>` while the gallery is still presented. Both host views resolve `reactViewController` via the responder chain (`UIView+React.m:282-292`) to the *same* presenting VC, which already has the gallery presented, so UIKit refuses the second `presentViewController:` and `_isPresented` is latched (`RCTModalHostViewComponentView.mm:149-165`) with no retry. The viewer appears only after the gallery is closed. Commit `03a3ec2` deliberately removed the earlier `onClose(); onSelect(index);` on a false premise ("the viewer stacks over it").

**Attempted fix (`1ccb818`, reverted in `ab8d7f4`).** Called `setShowGallery(false)` alongside `setActiveMediaIndex(index)` in the same handler. Rejected because (a) both prop updates land in the same Fabric mount transaction, producing a same-runloop `dismissViewController:` + `presentViewController:` on one VC — the exact "attempt to present while presenting" race `src/components/LimitSheet.tsx:95-104` and CLAUDE.md already document a 280ms-defer workaround for, with the same latched-`_isPresented` dead-tap symptom; (b) it silently reverted the shipped behavior that swiping out of the viewer returns to the gallery grid; (c) the committed test imported the untracked harness and added a `tsc` error to the committed tree.

**Proposed fix.** Either:
- (a) close the gallery, then mount the viewer only when the gallery's `onDismiss` fires (RN `Modal` supports `onDismiss` on Fabric; unused anywhere in the repo today), mirroring `LimitSheet.tsx:95-104` / the existing `membersSheetMounted` deferred-mount idiom in this same screen (`:1586/:1597/:1602/:2914-2916`); or
- (b) render `<MediaViewerModal>` inside `MediaGalleryModal`'s own subtree while the gallery is open, so its `reactViewController` resolves to the gallery's already-presented VC and the nested present succeeds without closing the gallery. This also preserves "swipe out returns to the grid".

Option (b) matches the behavior `03a3ec2` intended. Either way, verify on a real iOS device or simulator — jest cannot observe the native presentation conflict.

### 7. `declineInvite` silently no-ops under RLS (high)

`src/screens/app/NotificationsScreen.tsx:311-320`; `supabase/migrations/20260515232500_capture_capsule_rls_and_helpers.sql:91-94`.

**Bug.** Decline deletes the pending `capsule_members` row as the invitee, but `capsule_members_delete` is owner-only and never redefined later. The delete matches zero rows, PostgREST returns `{ error: null }`, the success branch marks the invite notification read, and the card disappears forever while the pending row and the owner's ghost "Pending" member survive. The `20260802120000` migration's comment claiming ManageMembersScreen is "the only capsule_members DELETE call site" is already false.

**Attempted fix (`4d09ac0`, reverted in `e25ed0d`).** Two-sided: `.select('id')` after `.delete()` treating zero rows as failure, plus migration `20260915130000_capsule_members_delete_self_decline.sql` extending the policy to `or (user_id = auth.uid() and joined_at is null)`. Reviewer found both production changes **correct** (the tombstone trigger's self-leave early return means a decline writes no revocation row, so re-invites still work) but rejected because: the only committed test was a jest test depending on the untracked harness; the RLS half — the actual substance — had zero committed coverage despite `src/lib/capsulesUpdateColumnGrants.test.ts` being the established pattern for exactly this; and a comment at `NotificationsScreen.tsx:315-316` stated the policy is owner-only, which the same commit's migration made false.

**Proposed fix.** Re-land the same two source changes (`git show 4d09ac0` has them), fix the stale comment, and replace the jest test with a Tier 0 `src/lib/*.test.ts` throwaway-Postgres test of the new DELETE policy modeled on `capsulesUpdateColumnGrants.test.ts`: invitee can delete own pending row (1 row); joined member cannot self-remove (0); unrelated user cannot delete someone else's pending row (0); owner delete unchanged (1). The implementer ran exactly those four cases locally and just did not commit them.

### 8. `push_token` survives sign-out; shared device leaks pushes across accounts (high, security)

`src/hooks/usePushNotifications.native.ts:107-110` (sole writer); `src/hooks/useAuth.ts:66-84` (SIGNED_OUT cleanup omits it); sign-out call sites `ProfileScreen.tsx:466`, `SettingsScreen.tsx:297-298`.

**Bug.** `registerToken()` only ever does `UPDATE users SET push_token = T WHERE id = userId`; nothing clears it on sign-out and there is no uniqueness constraint. User A signs out, User B signs in on the same device (OS permission already granted, so no prompt), and both rows hold token T. A cron push for a capsule only A belongs to (e.g. `unlock-capsules`' `capsule_members -> users(push_token)` join) delivers A's capsule title to B's device. The "tap navigates without a membership check" half of the original claim was refuted: `CapsuleDetailScreen`'s RLS-gated select already blocks a non-member from seeing contents.

**Attempted fix (`da38749`, reverted in `14db716`).** Added `clearPushToken(userId)` and called it before `supabase.auth.signOut()` in both call sites. Reviewer accepted the ProfileScreen half as correct (the `users` UPDATE grant is still table-wide, and the session is live at that point — note that doing this inside `useAuth`'s SIGNED_OUT handler would run after the session is gone and RLS would no-op it). Rejected because: the test only asserted `clearPushToken` issues the expected `update({push_token:null})` — tautological, and it passes with both call sites reverted; the SettingsScreen call site is dead by construction (it runs after `delete_my_account` has destroyed the auth user, so it's an awaited network call with a dead JWT against a deleted row); the unconditional clear breaks multi-device — signing out on device 1 nulls the token device 2 registered; and the test depended on the untracked harness.

**Proposed fix.** Keep `clearPushToken` but (1) call it only from ProfileScreen's Sign Out, before `signOut()`, with a short timeout so the button cannot hang; (2) guard it: read this device's `getExpoPushTokenAsync()` and clear only `where id = uid and push_token = <this token>` so another device's registration survives; (3) test the behavior, not the helper — a component test that presses Sign Out and asserts the `users` update happens before `auth.signOut`, or a Tier 0 test of a pure "should clear?" decision if the guard is extracted. Longer-term, a DB-side "one token, one user" clear-on-write would close the gap for any future writer.

### 9. Profile / Alerts render blank after a Tabs remount (high, never attempted)

`src/hooks/useCachedFetch.ts:92-107`; `src/screens/app/ProfileScreen.tsx:275-282,318-319`; `src/screens/app/NotificationsScreen.tsx:124-161`; trigger at `src/screens/app/PreviewScreen.tsx:264-267`.

**Bug.** Both screens keep their real render state (`profile`/`stats`, `notifications`/`pendingMap`) in local `useState`, populated only as a side effect *inside* the `useCachedFetch` fetcher. On a fresh mount with a warm cache (`< 15 min` TTL), the hook's focus effect takes the cache-hit branch, sets its own `data`, and never calls the fetcher — so the local state stays empty. Neither screen reads `data` (`const { loading, refresh } = useCachedFetch(...)`). The multi-select "Add to Capsule" flow does `navigation.replace('Tabs', { screen: 'Home' })`, creating a new Tab.Navigator and remounting both screens. Result: blank hero card, 0/0/0 stats, "all caught up" with real unread alerts sitting unused in `data`.

**Proposed fix.** Have both screens derive `profile`/`stats` and `notifications`/`pendingMap` from the hook's `data` (via `useMemo`, or a `useEffect` that mirrors `data` into local state when non-null) instead of assigning them as a side effect inside the fetcher. That is a contained change in two screens and needs no hook change. A jest test can pin it: pre-warm `cache.set('profile', ...)`, mount `ProfileScreen`, and assert the profile name renders without the fetcher being called.

## Refuted

Do not re-report these. Each was verified against the actual code (and, where relevant, the installed library source) and the claimed symptom has no reachable path.

**`MediaViewerModal` seeds `currentIndex`/`translateX` from `startIndex` only at mount, ignoring later prop changes** (`CapsuleDetailScreen.tsx:669-796`). The mechanics are true, but `startIndex` is `activeMediaIndex`, whose four writers are all touch handlers underneath the viewer's full-screen, touch-capturing `<Modal>`. Every exit path (header close, swipe-down, Android back, deleted-item branch) calls `onClose -> setActiveMediaIndex(null)`, unmounting the viewer, so each open is a fresh mount with the right index. No interaction can change `startIndex` on a mounted instance.

**Pending (unaccepted) invitees can upload — media/storage INSERT policies never check `joined_at`** (`20260716120000_capsule_start_date.sql:18-29,39-50`). The policies really do omit the check, but `joined_at` is not a security boundary against this attacker: `20260722120000_audit_rls_hardening.sql:46-48` grants `update (joined_at)` to `authenticated` with no WITH CHECK, so a pending invitee accepts with the same one-line PATCH the Accept button sends. Any authenticated user who knows a capsule UUID can also self-insert a fully-joined contributor row via the documented QR/deep-link join design. The fix would raise the attacker's ceiling by zero and would drop/recreate the live storage upload policy with no SQL tests to catch a malformed WITH CHECK. The repo's own audit rated the read-side twin (F17) low.

**Reset-password deep link swaps the signed-in user without `SIGNED_OUT`, leaking cached data** (`src/hooks/useDeepLinks.ts:91`). auth-js's `_saveSession` unconditionally deletes the PKCE `code-verifier` as its first action (`GoTrueClient.js:3978-3983`). `resetPasswordForEmail` is only callable from `LoginScreen`, which mounts only when signed out; every path from signed-out to signed-in goes through `_saveSession` and wipes the verifier. So `exchangeCodeForSession` on a signed-in device always throws `AuthPKCECodeVerifierMissingError` before any network call, the toast fires, and no session swap occurs. The proposed fix (diffing user id on every auth event) would additionally fire `uploadQueue.reset()` + `cache.clear()` on every cold boot's `INITIAL_SESSION`, discarding restored upload-queue state.

## Harness

Before this hunt the repo had 14 bare `node:assert` scripts in `src/lib/*.test.ts` and no way to run them, no component tests, and `CLAUDE.md` said "No test suite or linter configured yet." What exists now:

**Tier 0 — pure logic (`npm run test:lib`).** Runs every `src/lib/*.test.ts` under `npx tsx`, one process per file. 18 files, all green, ~10s total (two of them boot a throwaway Postgres, see below). Files are top-level `node:assert/strict` scripts with a closing `console.log('<name>: all assertions passed')` — no `describe`/`it`, no registration step. **This is the preferred place for regression tests**: when a bug is traced to logic tangled inside a screen, extract the decision into a pure `src/lib/<name>.ts`, import it back, and pin it there. `src/lib/zoomMath.ts` (pinch/pan math lifted out of the media viewer) and this hunt's `galleryLayout.ts` / `mergeCapsuleUpdate.ts` are worked examples.

**Tier 0, SQL flavor.** `src/lib/tombstoneTriggerCascadeDelete.test.ts` and `src/lib/capsulesUpdateColumnGrants.test.ts` `initdb` a throwaway Postgres 18 cluster (found via PATH or `/Library/PostgreSQL/18/bin`), load the real migration SQL by text extraction, exercise it as `authenticated`, and tear down. Use this shape for any RLS/trigger/RPC fix. They hard-fail without a local Postgres, so `npm test` currently requires one; CI will need Postgres on the runner or a skip-with-warning.

**Tier 1 — component/interaction (`npm run test:components`).** `jest` with `jest-expo/ios` + `@testing-library/react-native@14` (async API: `await render(...)`, `await fireEvent.press(...)`, matchers built in). Config: `jest.config.js` (testMatch scoped to `src/**/__tests__/**/*.test.@(ts|tsx)` so it never picks up Tier 0 scripts; `moduleNameMapper` for the un-hoisted `@expo/vector-icons`), `babel.config.js` (mandatory — `require.resolve('expo/internal/babel-preset')`), `test/setup.ts` (mocks for `expo-video`, `react-native-purchases(-ui)`, `@react-native-async-storage/async-storage`; dummy Supabase env), `test/renderWithProviders.tsx` (`SafeAreaProvider > ThemeProvider > NavigationContainer > TourProvider`).
