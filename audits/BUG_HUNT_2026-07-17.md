Six parallel domain reviewers (auth/session, upload pipeline, CapsuleDetail/cache, core screens, groups/recurrence, server-side) produced 30 raw findings; every finding was then adversarially re-verified against the actual code (and, for the recurrence claim, an executed reproduction script). 29 confirmed, 1 downgraded to plausible-edge-case. ## Critical

### 1. Account deletion wipes other users' capsule media before the DB transaction, with no rollback (S4)
`src/screens/app/SettingsScreen.tsx:162-197`
`confirm()` removes every storage object the user contributed — **including photos in other people's capsules** — *before* calling the `delete_my_account` RPC. If the RPC then fails (transient network/DB error), the account survives, but other members' capsule photos are permanently gone: `media` rows point at dead storage keys, and nobody who owns those capsules asked for anything.
**Fix:** call `delete_my_account` first; remove storage objects only after it succeeds (or move storage cleanup server-side into the RPC/a queued job). The avatar removal can stay best-effort.

## High

### 2. Recurrence math interprets UTC anchors in device-local time — schedules are written hours wrong (G1) — *empirically verified*
`src/lib/recurrence.ts:38-71`, written to DB by `src/lib/groups.ts:121,228,272`; anchor captured inconsistently in `src/screens/app/CreateGroupScreen.tsx:68-85`
`anchor_hour/minute` are documented UTC, but `computeNextOccurrence` uses local `setHours`/`new Date(y,m,d,h,m)`. Client-side calls (`createGroup`, `updateGroup`, `resumeGroupRecurrence`) write the resulting local-interpreted instant straight to `next_capsule_at`. Reproduction (TZ=America/New_York, weekly group created Fri 23:30 EDT): client writes Fri 07:30 UTC, the cron's own UTC copy would compute Fri 03:30 UTC, and the user expected Fri 23:30 EDT — all three disagree. `defaultAnchor()` also mixes local `getDay()` with `getUTCHours()`, so the anchor itself can describe two different calendar days.
**Fix:** make `recurrence.ts` fully UTC (`Date.UTC`, `getUTCDay`, `setUTCHours`, UTC clamping) and mirror the change into the duplicated copy in `supabase/functions/create-group-capsules/index.ts`; capture `defaultAnchor()` entirely from UTC fields; then one-time recompute `next_capsule_at` for existing non-manual groups.

### 3. "Capsule unlocked" delivery is a single unguarded push — one transient failure loses it forever, and there's no in-app record even on success (X1)
`supabase/functions/unlock-capsules/index.ts:35-43,133-170`
The unlock UPDATE commits first (idempotent — the row can never be claimed again), then `sendExpoPush` runs outside any try/catch as a bare `fetch` loop. Nothing anywhere inserts a durable `type: 'unlock'` notifications row (only `unlock_reminder` exists in this function) — so the moment the capsule's whole payoff arrives, delivery rests on one unretried network call.
**Fix:** insert `unlock` notification rows for all joined members before pushing (pattern already used by every other event type), and wrap the push in try/catch.

### 4. Upload queue has no timeouts — one hung upload permanently wedges all uploads app-wide (U5)
`src/lib/uploadQueue.ts:73-102,202-233`
`work()` is a single global sequential loop; `uploadFile` (native `FileSystem.uploadAsync`, web `fetch`), `resizeForUpload`, and the media insert have no timeout. RN's fetch/uploadAsync never time out on a dead connection. A hang leaves `working=true` forever; every later `enqueue()` from any capsule returns silently; the stuck task never reaches `failed` so no Retry UI ever appears. Only force-quit recovers (losing the in-memory queue).
**Fix:** wrap `runTask` in a `Promise.race` timeout (e.g. 2–5 min) that rejects into the existing `failed`/Retry path.

### 5. Capsule delete wipes storage, then ignores the row-delete result (S3)
`src/screens/app/EditCapsuleScreen.tsx:153-168`
`confirmDelete` removes all media storage first, then `await supabase.from('capsules').delete()` with no error check, then navigates as if successful. On a failed row delete: capsule still exists everywhere, every photo in it is permanently gone. `handleSave`/`handleArchive` in the same file check their errors — this one path doesn't.
**Fix:** check `{ error }` and surface failure; better, delete the row first and storage after (orphaned storage is recoverable; orphaned rows with dead keys are user-visible data loss).

### 6+7. Proximity mode skips the start-date/uploads-deadline ordering validation — capsules whose upload window never opens (S1, S2)
`src/screens/app/CreateScreen.tsx:122-150`, `src/screens/app/EditCapsuleScreen.tsx:94-109`
Every date-ordering check, including `startDate >= contribLockDate`, sits inside `if (unlockMode !== 'proximity')`. Both fields render and persist in proximity mode, and both RLS gates apply regardless of unlock mode — so a proximity capsule with Starts=Aug 20, Deadline=Aug 10 is accepted and can never receive a single photo.
**Fix:** hoist the `startDate`/`contribLockDate` mutual check (both screens) outside the proximity guard; only the unlock-date comparisons belong inside it.

### 8. Password-reset deep link dead-ends signed-out users on Home (A1)
`src/hooks/useDeepLinks.ts:8-31`
After `setSession()` succeeds, `navigate('ResetPassword')` fires while `AuthNavigator` is still mounted (the React re-render to `AppNavigator` happens a tick later). `ResetPassword` only exists in `AppNavigator`, so the navigation is dropped; the user ends up silently signed in on Home, never setting a new password. The signed-out case is exactly the "forgot password" mainline.
**Fix:** retry the navigate until the route resolves (bounded retry loop keyed on whether the current navigator contains the route), or defer navigation until the session-driven navigator swap has committed.

### 9. Sign-up shows a false "check your email" for already-registered accounts (A3)
`src/screens/auth/SignUpScreen.tsx:58-72`
Supabase's anti-enumeration behavior returns success + `session: null` + an obfuscated user for an existing confirmed email. The code treats any `session === null` success as "confirmation email sent" — the user waits for an email that never comes.
**Fix:** on session-less success, check `data.user?.identities?.length === 0` and route to the existing "already registered → Sign in instead" copy/action.

### 10. MediaViewerModal shows the wrong photo (and targets reactions at the wrong media) when the list changes underneath it (D1)
`src/screens/app/CapsuleDetailScreen.tsx:557-576,676`
`currentIndex`/`translateX` are set once from `startIndex`; no effect resyncs them when `items` changes. Background upload completions (a very common overlap: add photos, then browse while they land) prepend rows and shift every index — the open viewer silently displays a different photo, and a reaction tapped there writes to the wrong media id.
**Fix:** track the viewed item by `id`; derive index via `findIndex` on every `items` change (close the modal if the id disappears).

## Medium

Fix: carry the `t` param through into the render-API query string.
12. **D5 — Full-screen viewer can permanently show upscaled thumbnails.** Grid (`:921,1757`) and viewer (`:742`) use the same `cacheKey: storage_key` for different-resolution bytes; whichever loads first owns the disk-cache slot. Fix: suffix keys per size (`:thumb`/`:full`).
13. **D2 — A hung fetch that finally resolves overwrites the cache after a successful forced retry.** `useCachedFetch.fetchOnce`'s `cache.set` has no identity guard (the `finally` guards only the registry). Fix: only `cache.set` when `inFlight.get(key) === promise`.
14. **D3 — Member changes in ManageMembers never reach the still-mounted CapsuleDetail.** No `cache.invalidate` in ManageMembersScreen, no focus-refetch in CapsuleDetail; stale avatar cluster and `existingMemberIds` silently block re-inviting the removed person. Fix: invalidate `capsule:${id}` on member mutations.
15. **D4 — Saved captions revert in the UI within the 3-minute media-cache window.** `saveCaption` never invalidates/patches `media:${capsuleId}`; any non-forced `fetchPhotos` rebuilds from the pre-edit cache. Fix: invalidate or patch the cached array on save.
16. **U1 — Captions typed on PreviewScreen are dropped on the "Create Capsule" empty-state path.** `goCreateCapsule` forwards raw `items` without merging `captions`; CreateScreen reads `m.caption`. Fix: merge captions into the forwarded array.
17. **A2 — Invite links tapped while signed out are silently discarded.** `useDeepLinks` returns on no-session with no stash (unlike the share-intent path, which has one for exactly this). Fix: stash the pending capsule id; drain on sign-in.
18. **A4 — Cold-start can flash the Welcome screen at signed-in users.** The 1.5s native fallback settles `session=null` if SecureStore restore is slow, bouncing through AuthNavigator before the real session lands. Fix: on timeout, release `loading` without asserting a null session.
19. **S5 — Friend-request decline has no failure rollback/toast.** `FriendsScreen.decline()` discards `removeFriendship`'s error (the codebase's own optimistic-action pattern, used in NotificationsScreen, handles this). Fix: mirror `declineFriend`'s rollback+toast.
20. **S6 — Blocked-users screen can show a stale list after same-size churn.** `load`'s `useCallback` keys on `blockedIds.size`, closing over stale set contents. Fix: key on contents (or drop the memoization).
21. **X2 — A paused-and-overdue group defeats the cron's EXISTS gate forever.** The gate (`20260709130000_cron_exists_gates.sql:63`) lacks the `recurrence_paused_at is null` filter the function itself applies — per-minute cold starts resume permanently. Fix: add the filter to the gate (new migration re-registering the cron).
