# Live Activity Countdown — Design Spec

**Date:** 2026-07-24
**Status:** Approved, ready for implementation plan

## Context

While a capsule is open for photos there is nothing on the phone reminding anyone of it. The core loop depends on people actually shooting during the event, but the app is only present if someone remembers to open it — the contribution nudges (7d/3d/1d) are the only pull, and they're notifications that get swiped away.

Once solves this with an iOS **Live Activity**: a persistent lock-screen / Dynamic Island card for the duration of the event, showing the capsule title, a ticking "2h 39m left" countdown, and a one-tap camera button. It's ambient rather than interruptive — it sits on the lock screen for the whole event instead of firing once and vanishing.

This spec adds that: a per-capsule Live Activity that runs while the capsule is open for contributions, counting down to the uploads deadline, with a quick-camera action.

## Goals

- A Live Activity on the lock screen + Dynamic Island while a capsule is open for photos.
- Countdown to the **uploads deadline** (`contribution_lock_at ?? unlock_at`), not to the reveal — the camera button is only meaningful while you can still shoot.
- Owner sets a per-capsule default; any member can override it for their own device.
- Free for all tiers.
- Zero backend: no APNs key, no edge function, no token table.

## Non-goals

- **No push-to-start.** The activity is started by the app on-device. It will not appear on a member's phone until they open the app at least once during the contribution window. Accepted, explicitly chosen — push-to-start requires an Apple `.p8` key, an ES256-signing edge function talking directly to APNs (Expo's push service cannot send `apns-push-type: liveactivity`), per-device push-to-start token sync, and iOS 17.2+. The native module API is shaped so this can be layered on later without rework.
- **No home-screen widget.** Live Activity only.
- **No reveal-countdown phase.** The activity ends at the uploads deadline. The unlock moment already has its own push (`unlock-capsules` + `unlock_reminder` tiers); duplicating it in a second surface adds no information.
- **No Android.** ActivityKit is iOS-only. The JS layer no-ops elsewhere.
- **No images in the activity.** Avoiding them means no App Group is needed — everything travels in the activity's own attributes/content state.

## Approach: `@bacons/apple-targets` + a local Expo module

A Live Activity needs a **Widget Extension target** in the Xcode project. `ios/` is gitignored and regenerated by `expo prebuild`, so the target must come from a config plugin — it can never be hand-added to the pbxproj.

Three options were evaluated:

| | Approach | Verdict |
|---|---|---|
| **A** | `@bacons/apple-targets` v5 (requires SDK 53+) for the widget target, plus a local `modules/expo-live-activity` Expo module for the ActivityKit calls | **Chosen.** Swift sources live in `targets/` *outside* `ios/`, surviving `prebuild --clean`. Mirrors the existing `modules/expo-dual-camera` and `modules/expo-video-stitcher` precedent. No SDK bump. |
| **B** | `@kingstinct/react-native-activity-kit` | Rejected. Published at **v0.0.10**, and requires adding `react-native-nitro-modules` to the build. Too immature for an app heading to TestFlight. |
| **C** | Official `expo-widgets` | Rejected. Earliest published version is `56.0.20` — it requires **Expo SDK 56+**; this app is on **54**. Upgrading two majors would collide with the `react-native+0.81.5.patch` (TurboModule Hermes crash fix), `expo-share-intent` 5.1.1 (v6 requires SDK 55+), and the local dual-camera module. Blast radius wildly exceeds the feature. Revisit if/when the app upgrades past SDK 56. |

## Data model

```sql
alter table public.capsules
  add column live_activity_enabled boolean not null default true;

-- Existing capsules opt out, matching the owner_preview_locked precedent: a live
-- capsule must not suddenly start appearing on members' lock screens on app update.
-- Runs once at migration time, so this is every pre-existing row.
update public.capsules set live_activity_enabled = false;

alter table public.capsule_members
  add column live_activity_override boolean;  -- null = inherit the capsule default

grant update (live_activity_override) on public.capsule_members to authenticated;
```

**The `grant` is mandatory, not hygiene.** Verified against production: `capsule_members` has table-wide SELECT and INSERT for `authenticated` but **no table-wide UPDATE** — the July 2026 audit hardening (`20260722120000_audit_rls_hardening.sql`) revoked it and granted back only `joined_at`. Without the column grant, every override write fails `42501 permission denied`, and it would fail for the *whole statement*, not just that column.

Conversely `capsules` **does** still have table-wide SELECT and UPDATE, so `live_activity_enabled` needs no grant and no policy change — the existing owner-UPDATE policy already governs who may write it.

`live_activity_override` inherits table-wide SELECT/INSERT automatically, so it is readable with no extra grant.

**Effective value:**

```ts
effectiveEnabled = member?.live_activity_override ?? capsule.live_activity_enabled
```

### Default-on rationale

New capsules default to `true`. The feature's whole value is being present during the event without anyone having to find a setting, and a toggle defaulting to off inside "More options" would be used by nobody. iOS retains the real veto: the first activity triggers the system permission prompt (the dialog in the reference screenshot), and users can disable Live Activities per-app in Settings at any time. The per-member override is the in-app escape hatch.

## Native architecture

### `targets/liveactivity/` — the widget extension

- `expo-target.config.js` — `type: 'widget'`, `frameworks: ['SwiftUI', 'ActivityKit', 'WidgetKit']`.
- `CapsuleActivityAttributes.swift` — the shared attributes type.
- `CapsuleLiveActivity.swift` — the `Widget` + SwiftUI views: lock-screen/banner presentation, and Dynamic Island `expanded` / `compactLeading` / `compactTrailing` / `minimal`.

```swift
struct CapsuleActivityAttributes: ActivityAttributes {
    // static — fixed for the activity's lifetime
    let capsuleId: String
    let title: String
    let accentHex: String     // the VIEWING member's own accent color (users.accent_color via
                              // ThemeContext) — not the owner's. It renders on their lock screen,
                              // and accent color is a per-user preference in this app.
    let windowStart: Date     // for the progress bar's lower bound
    let deadline: Date        // contribution_lock_at ?? unlock_at

    struct ContentState: Codable & Hashable {
        var photoCount: Int
        var memberCount: Int
    }
}
```

**The countdown requires zero updates.** `Text(timerInterval: windowStart...deadline, countsDown: true)` and `ProgressView(timerInterval:)` are rendered and ticked by the system on-device. Combined with `staleDate: deadline` set at request time, an activity started once stays correct for the whole window even if the app never runs again. Only `photoCount` needs an `update()`.

### `modules/expo-live-activity/` — the ActivityKit bridge

A local Expo module (autolinked from `modules/`, same as the two existing ones). `ios/ExpoLiveActivityModule.swift`:

| Function | Purpose |
|---|---|
| `isSupported(): boolean` | iOS ≥ 16.2 **and** `ActivityAuthorizationInfo().areActivitiesEnabled` |
| `start(config): string` | `Activity.request(...)`, returns the activity id |
| `update(capsuleId, state)` | Pushes a new `ContentState` |
| `end(capsuleId, immediate)` | Ends with `.immediate` or `.default` dismissal |
| `listActive(): {capsuleId, activityId}[]` | Reads `Activity<CapsuleActivityAttributes>.activities` |

`index.ts` guards `Platform.OS !== 'ios'` and wraps `requireNativeModule` in try/catch, so web, Android, and Expo Go fall back to `isSupported() === false` and every other call becomes a no-op — the exact idiom already used by `modules/expo-dual-camera/index.ts`.

Everything is `@available(iOS 16.2, *)`-guarded, because the app's deployment target is 15.5 (pinned in `app.json` via `expo-build-properties` for `react-native-zip-archive`).

### Sharing the attributes type

`CapsuleActivityAttributes` must be compiled into **both** the widget extension and the main app target — ActivityKit matches activities by concrete type, so two separately-declared identical structs in different modules do not interoperate. This is the known friction point of this setup and the single highest-risk implementation detail. The plan will settle on one shared file compiled into both targets (rather than duplicated declarations) and verify it by round-tripping `listActive()` after a `start()` on a real device.

## Lifecycle: reconciliation, not scattered start calls

One hook, `src/hooks/useLiveActivities.ts`, called once from `App.tsx` alongside `usePushNotifications` / `useRevenueCat`. It **reconciles** desired state against actual state rather than firing `start()` from many call sites:

```
on app foreground (AppState 'active') and on capsule-list load:
  desired = capsules where effectiveEnabled
                     and now ∈ [contribution_start_at ?? created_at, deadline)
                     and status != 'unlocked'
  actual  = await liveActivity.listActive()

  for c in desired \ actual : start(c)
  for a in actual  \ desired: end(a)          // deadline passed, opted out, unlocked, left
  for c in desired ∩ actual : update if photoCount changed
```

Truth for "what is currently running" comes from the native `Activity.activities` list via `listActive()`, **not** from an AsyncStorage mirror — the OS can dismiss an activity on its own (user swipe, 12h expiry, force-quit), and a JS-side mirror would drift and then try to `update()` something that no longer exists.

`photoCount` refreshes on foreground and when `uploadQueue` drains (it already fires a toast at that point — same hook-in). Between those, the count is stale; the countdown is not, since the system ticks it. This staleness is the accepted consequence of the no-server decision.

`deadline = contribution_lock_at ?? unlock_at`.

## UI surfaces

**`CreateScreen` → "More options"** — a "Live countdown on lock screen" switch, defaulting to on, next to "Keep it a surprise". Included in the collapsed one-line summary the disclosure already renders. Written through `create_capsule_with_owner`, which needs a new trailing `p_live_activity_enabled boolean default true` parameter — and per the `contribution_start_at` precedent (`20260716120000_capsule_start_date.sql`), the migration must **drop the existing overload before `create or replace`**, or the added parameter creates two coexisting overloads and PostgREST fails the original call with `PGRST203`.

**`EditCapsuleScreen`** — the same row, owner-editable, loaded from and saved to `live_activity_enabled`.

**`CapsuleDetailScreen`** — a member-facing row shown **while the capsule is live** (inside its contribution window). This is where the feature is discovered and where `live_activity_override` is written. It shows the effective state and writes the override on toggle. Hidden entirely when `!isSupported()` — no dead toggle on web, Android, iOS < 16.2, or when the user has disabled Live Activities system-wide.

All three surfaces toggle through one handler so a tier gate could later be added in exactly one place, should the free-for-everyone decision be revisited.

## Deep links

The activity is tappable in two places, both new routes in `useDeepLinks` (which today handles only `join/` and `reset-password`):

| Target | URL | Behavior |
|---|---|---|
| Card body | `capsule://capsule/<id>` | Navigate to `CapsuleDetail` |
| Camera button | `capsule://capsule/<id>/camera` | Navigate to the Camera tab with `targetCapsuleId` preselected |

The camera route needs no new screen work — `CameraScreen` already accepts `targetCapsuleId` and threads it into its Preview navigation so the capsule arrives preselected. Both routes must handle the signed-out case the same way the join link does (stash and drain after sign-in) rather than dropping the tap.

## Error handling

- `start()` throwing (permission denied, budget exhausted, unsupported) is **silent to the user** — this is ambient decoration, not an action they requested in the moment. It goes to `reportError(err, { where: 'liveActivity.start' })` per the established convention for swallowed errors.
- A user toggling the override **is** a user-initiated mutation, so a failed write toasts, per the standing rule.
- `isSupported()` false ⇒ no UI, no calls, no errors.

## Testing

- **Pure logic, unit-tested** with `node:assert/strict` run via `npx tsx`, matching the `src/lib/recurrence.test.ts` precedent (this repo deliberately has no test framework): the reconciliation diff (desired vs actual → start/end/update sets), `effectiveEnabled` resolution across all four override/default combinations, and deadline derivation including the `contribution_lock_at` null fallback.
- **Device verification** is unavoidable for the rest — the widget extension, the shared-attributes round-trip, the Dynamic Island presentations, and the deep links cannot be exercised in Expo Go or the simulator's absence of a lock screen. Requires a fresh dev/EAS build.

## Risks

1. **New iOS target means new signing.** This has already bitten this project once: `iosShareExtensionName: "Capsule"` sanitized to a target name colliding with the main `Capsule` target, which made EAS/fastlane sign the main app with the share-extension's provisioning profile and failed the build with three profile-mismatch errors. The widget target takes a distinct name and bundle id (`com.markdickson.capsule.liveactivity`) and must be registered alongside the main app and the existing share extension in `eas credentials`.
2. **Requires a fresh dev/EAS build** — a new native target is invisible to the current binary and to Expo Go, same as dual camera.
3. **iOS 16.2+ only** against a 15.5 deployment target; guarded, and the feature is simply absent below that.
4. **Shared-attributes-type wiring** — see above; the highest-risk detail, verified on device.
5. **`@bacons/apple-targets` is a third-party plugin** carrying its own Xcode-parsing implementation, and it warns that anything changed in Xcode outside the target folder is overwritten on the next `prebuild --clean`. Acceptable: it is the only viable route on SDK 54, and it is the same class of dependency the project already accepts for the share extension.
6. **Stale `photoCount`** between foregrounds. Accepted.

## Follow-ups (explicitly out of scope)

- Push-to-start via APNs, so the activity appears without the app being opened.
- Server-driven `photoCount` updates (same APNs pipeline).
- A reveal-countdown phase, or a home-screen widget for long-horizon capsules.
