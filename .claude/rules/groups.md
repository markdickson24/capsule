## Groups

Named member sets with an optional recurrence schedule that auto-creates capsules — e.g. a family wanting a fresh time-locked capsule every month without manually starting one.

**Schema:** `groups` (id, name, `created_by` → `users(id)` **on delete cascade**, `recurrence_interval` [`weekly`/`monthly`/`yearly`/`manual`], `unlock_duration_hours`, `next_capsule_at`, `last_capsule_at`, `created_at`, `anchor_weekday`/`anchor_day_of_month`/`anchor_month`/`anchor_day`/`anchor_hour`/`anchor_minute`, `recurrence_paused_at`, `reminder_lead_hours`, `next_reminder_sent_at` — see "Fixed calendar anchors" below); `group_members` (`group_id`, `user_id`, `joined_at`, unique on the pair); `capsules.group_id` — nullable FK set on any group-originated capsule.

**Group creation goes through the `create_group_with_creator(...)` RPC** (`20260718091000_create_group_with_creator.sql`), not a direct client insert — same fix pattern as `create_capsule_with_owner`. `createGroup()` (`src/lib/groups.ts`) used to insert the `groups` row and the creator's `group_members` row as two separate requests; a failed second request left the group **orphaned with zero members and permanently invisible** (the `groups` SELECT policy is membership-gated via `get_my_group_ids()`). The RPC does both inserts in one `security definer` body (rollback on either failure) and generates + returns the UUID server-side; the client no longer generates it with `randomUUID()`.

**RLS:** `get_my_group_ids()` (SECURITY DEFINER) avoids recursion on the `group_members` SELECT policy, same pattern as `get_my_capsule_ids()`. **`group_members` INSERT is creator-only**, via `is_group_creator(p_group_id)` (SECURITY DEFINER). The original policy also allowed `user_id = auth.uid()` — self-insert — a real privilege escalation: `capsules.group_id` is a plain readable column on every group capsule, and `get_my_capsule_ids()` includes *pending* memberships, so being merely invited to one group capsule let you read the group's UUID and self-join it, then auto-join every future recurring capsule. Closed in `20260710000000_groups_rls_selfinsert_fix.sql`. **DELETE still allows creator-or-self** (leaving a group is legitimate). `is_group_creator` and `check_cron_secret` existed only in the live DB with no prior migration, captured verbatim in `20260710020000_capture_group_helpers.sql` — treat any future groups-related live/migration mismatch the same way (verify with `pg_get_functiondef` before assuming the migration is current).

**Auto-join is standing consent.** Joining a group means consenting to its future capsules — every group capsule, manual or cron-created, inserts other members already-joined (`joined_at` set at insert), not as a pending invite. The `notify_on_invite` trigger has two branches: non-owner + `joined_at IS NULL` → `'invite'` notification; non-owner + `joined_at IS NOT NULL` + capsule has a `group_id` → `group_capsule` notification (new `notifications.type`, added to `notifications_type_check`) — mutually exclusive since `joined_at` is either null or not. `NotificationsScreen` renders `group_capsule` with `people-circle-outline`, capsule-nav (tap → `CapsuleDetail`). `send-invite-push` reads `capsule.group_id`/`groups(name)` and swaps copy to "New capsule for `<group>`" (nothing to accept).

**`create-group-capsules` cron** (`supabase/functions/create-group-capsules`), every minute like other crons:
- **Claims each due group atomically first** — advances `next_capsule_at`/`last_capsule_at` gated on `next_capsule_at <= now()`, proceeds only for matched rows (mirrors `unlock-capsules`' claim-and-stamp) — safe against overlapping ticks.
- **Re-checks the creator's Pro tier every tick, right after the claim.** Setting a real recurrence requires Pro at creation time (`guard_group_recurrence` trigger), but nothing re-verified it on each subsequent firing — a lapsed/downgraded creator's group would otherwise auto-create capsules forever, with unlimited member fan-out since it runs as `service_role` (bypasses `enforce_member_limit`). Due-groups query embeds `owner:users(subscription_tier)`; non-`'pro'` → `processGroup` returns immediately (no insert/fan-out/awards/push). **The claim is deliberately NOT released on this skip path** — `next_capsule_at` already advanced, so a lapsed group is skipped once per cycle, not retried every minute (PN-1).
- **Every insert after the claim is checked; failures roll back.** A failed `capsule_members` insert (or zero members) deletes the just-created capsule and resets `next_capsule_at`/`last_capsule_at` to pre-claim values, so the next tick retries instead of skipping a cycle or leaving an RLS-invisible, members-less capsule.
- **Seeds 4 default awards directly** — `superlative_categories` rows inserted `status='live', is_default=true` from a `general`-occasion pool mirrored verbatim from `src/lib/awardPool.ts` (group capsules have no `occasion` column; service role can't call the owner-gated `set_default_superlatives` RPC).
- **Pushes chunked ≤100** via a local `sendExpoPush()`, same pattern as `unlock-capsules`/`send-superlative-pushes`.
- **Titles:** `"{name} — {Month Year}"` except weekly groups, which get day granularity (`"{name} — July 20, 2026"`, via `capsuleTitleDate`) — a month-year title collides 4–5×/month for weekly recurrence (GROUPS.md #15).
- **Auth uses the shared `requireCronSecret` helper** (`supabase/functions/_shared/cronAuth.ts`), like every other cron now. ⚠️ It used to call the `check_cron_secret(provided)` SECURITY DEFINER RPC (reads `vault.decrypted_secrets`, returns the comparison **to the caller**) — exposed in `public` with EXECUTE left on `authenticated` (`20260718120000_revoke_anon_rpc_execute.sql` revoked only `anon`), so any signed-in user could POST `/rest/v1/rpc/check_cron_secret` in an unrate-limited loop as a **guess oracle for the project-wide `CRON_SECRET`** — the sole credential for all seven `verify_jwt=false` cron functions — with a non-constant-time `=`. `20260802120100_security_hardening.sql` revokes EXECUTE to `service_role` only and hashes both sides. **New cron function → use `requireCronSecret`; never publish a secret comparison through a `public`-schema RPC.** This reads the `CRON_SECRET` env var (not Vault) — must stay in sync with the Vault entry the cron sends.

**Manual create respects the schedule.** Starting a capsule manually for a group with a real recurrence (not `manual`) bumps `next_capsule_at` forward (`updateGroup(groupId, { recurrence: group.recurrence_interval })`, no `anchor` — `updateGroup` re-fetches the stored anchor and recomputes via `computeNextOccurrence`) right after creation, else the cron double-fires on the old schedule. Best-effort/non-fatal. The capsule is owned by whoever tapped create, not necessarily the group's creator (accepted asymmetry).

**`CreateGroupScreen`** (`src/screens/app/CreateGroupScreen.tsx`) — progressive disclosure, mirroring `CreateScreen`'s "More options" pattern exactly: Name, Add Members, the 4 recurrence chips always visible; anchor picker, unlock duration, reminder picker collapse behind a "Schedule details" toggle (shown only when `recurrence !== 'manual'`) with a one-line summary from `describeAnchor()` (`RecurrenceAnchorPicker.tsx`) + `unlockDurationLabel()` (`src/lib/groups.ts`). **Toggle is a plain row, no card/border** — revealed body is a flat `{ gap: 24 }` `View` whose children (`RecurrenceAnchorPicker`, a `section`-styled group each for Duration/Reminder) carry their own spacing, mirroring `CreateScreen.tsx`'s body (an earlier nested-card version read as "boxes inside boxes"). **Default Unlock Duration = day presets, not a date picker**: 3 day-count chips (1 week/1 month/3 months) + "Custom" revealing a numeric days `TextInput` (committed on blur or read on submit) — replaced a confusing `DatePickerField`-based approach. Single "Create Group" button. `createGroup()` returns optional `memberError: true` when the bulk member insert fails but group+creator succeeds — screen toasts rather than hard-failing. Navigates on success with `{ groupId, justCreated: true }`.

**Post-create nudge (`GroupDetailScreen`)** — `route.params.justCreated && memberList.length === 1` shows a dismissible "Add members" card (mirrors `CapsuleDetailScreen`'s post-create invite nudge: not persisted). Its "Add" button opens `ManageGroup` directly. The empty-capsules-list subtext reads "Your first capsule arrives `{date}` — or start one now." whenever a computed `nextDate` exists (any active non-manual, non-paused schedule) — independent of `justCreated`.

**`ManageGroupScreen`** (`src/screens/app/ManageGroupScreen.tsx`, route `ManageGroup { groupId }`, `animation: 'slide_from_bottom'`) — creator-only (`goBack()` for others), reached via a gear icon in `GroupDetailScreen`'s header (alongside the trash icon in `styles.headerActions`). Rename, recurrence change, and a member list with debounced add-search (excludes existing members + `blockStore.has(id)`, matching `InviteModal`'s pattern) and remove (trash → `ConfirmModal`; creator can't be removed) stay always visible. Same "Schedule details" disclosure as `CreateGroupScreen` (`detailsToggle`/`detailsBody` styles, flat unboxed body) collapses: calendar anchor (`RecurrenceAnchorPicker`), reminder lead (`ReminderLeadPicker`), "Upcoming Capsules" preview + Pause/Resume, Default Unlock Duration (same day-preset chips). Collapsed summary appends `· Paused` when applicable. Wires `updateGroup`/`addGroupMember`/`removeGroupMember` (`src/lib/groups.ts`, previously dead code). Invalidates `groups`/`group:${id}`/`group-members:${id}` on mutation. New members only appear in *future* group capsules.

**`handleSave` only passes `recurrence`/`anchor` to `updateGroup` when the schedule actually changed** (vs. a snapshot in `originalScheduleRef`) — `updateGroup` reschedules `next_capsule_at` and clears `next_reminder_sent_at` whenever `recurrence` is present in its args, so passing it unconditionally on a pure rename would risk a duplicate `group_capsule_upcoming` reminder.

### Fixed calendar anchors, pause/resume, and reminders

A recurring group's schedule is a **fixed calendar anchor**, not "N days/months/years from whenever it last fired": weekly picks a weekday, monthly a day-of-month, yearly a month+day, all sharing a fixed time-of-day (`anchor_hour`/`anchor_minute`, captured once at creation — no time-picker UI, since Groups UI only ever displays dates).

- **`src/lib/recurrence.ts`** — pure module exporting `computeNextOccurrence(interval, anchor, from)` and `computeUpcomingOccurrences(interval, anchor, from, count)`. Clamps short months/non-leap-years (a day-31 monthly anchor lands on Apr 30, then correctly uses day 31 again in May — recomputed fresh each cycle, doesn't stick). Verified via `src/lib/recurrence.test.ts` (`node:assert/strict`, run with `npx tsx` — this repo has no test framework configured, deliberate).
- **All anchor fields are UTC; the math is UTC-only both sides.** `recurrence.ts` uses only `Date.UTC`/`getUTC*`/`setUTC*`, never a local accessor, so `computeNextOccurrence` is timezone-independent — keeps the device-local client and the UTC Deno cron in agreement. `CreateGroupScreen.defaultAnchor()` and `ManageGroupScreen`'s seeded-anchor defaulting capture every field — weekday/dayOfMonth/month/day, hour/minute — from UTC getters (`now.getUTCDay()`/`getUTCDate()`/`getUTCMonth()`/`getUTCHours()`/`getUTCMinutes()`). **Don't reintroduce a local accessor on either side** — `src/lib/recurrence.ts` and `create-group-capsules`'s duplicate must stay in sync.
- **Duplicated verbatim into `create-group-capsules`** (Deno can't import `src/lib`) — same precedent as that file's `GENERAL_AWARD_POOL` mirroring `src/lib/awardPool.ts`. Keep the two copies in sync.
- **Pause/resume** — `recurrence_paused_at` (null = active). `pauseGroupRecurrence`/`resumeGroupRecurrence` (`src/lib/groups.ts`). The cron's due-groups query filters `recurrence_paused_at is null`, so a paused group's `next_capsule_at` simply stops advancing — no backlog. Resuming recomputes `next_capsule_at` from *now*, not from wherever it was frozen.
- **Upcoming-occurrences preview** is purely client-side (`computeUpcomingOccurrences`, no RPC) — both `GroupDetailScreen` (read-only "Next `<date>`" / "Paused" badge) and `ManageGroupScreen` ("Upcoming Capsules" list) recompute from `anchor + now()`, not `next_capsule_at`, so it can't distinguish a successful reschedule write from a silently-failed one (a failed write still toasts).
- **Every pre-existing group only has the anchor sub-field for its *original* `recurrence_interval` populated** — switching intervals leaves the others unset. `RecurrenceAnchorPicker`/`ManageGroupScreen`/`CreateGroupScreen` all default missing sub-fields to today's date (required by `computeNextOccurrence`, which throws otherwise) — any new call site reading a group's anchor needs the same defaulting.
- **Reminders** — `reminder_lead_hours` (null = off; 24/72/168 = 1 day/3 days/1 week) and `next_reminder_sent_at` (dedupe stamp, reset to null everywhere `next_capsule_at` changes: `updateGroup`, `resumeGroupRecurrence`, the cron's own claim). Cron's `processReminders()` (runs before capsule-creation each tick) claims due groups atomically, inserts a `group_capsule_upcoming` notification (new type; `capsule_id` null, `group_id` set) per joined member, pushed inline. Own try/catch (best-effort, matching `unlock-capsules`' `dispatchReminders`). `NotificationsScreen` renders `calendar-outline`, tap → `GroupDetail`; push handler routes `data.groupId` the same way.

**Data-layer error handling** (`src/lib/groups.ts`) — `deleteGroup`/`removeGroupMember` return `{ error?: string }` rather than `Promise<void>`; `GroupDetailScreen`'s handlers toast on failure and only navigate/invalidate on success. `listMyGroups`/`getGroup`/`getGroupMembers` `console.warn` (rather than throw) on a fetch error and fall back to an empty result — `useCachedFetch` has no error/retry path for a throwing fetcher (a throw just yields `loading:false` + `data:null` plus an unhandled-rejection warning, not a retry prompt), so throwing here would only add noise.

**Ownership safety net (groups and capsules).** `groups.created_by` and `capsules.owner_id` are both `on delete cascade` to `users(id)` — deleting an owner used to silently delete every group/capsule they owned for every other member too, with no warning. `delete_my_account` handles both: immediately before the final `auth.users` delete, every group created (`20260710030000_delete_account_group_transfer.sql`) and every capsule owned (`20260711170000_delete_account_capsule_transfer.sql`) is reassigned to another existing member — oldest-`joined_at`, deterministic (for capsules, another **joined**, not pending, member; bumps their `capsule_members.role` to `'owner'`). With no other joined member, it falls through to the existing `delete from capsules where owner_id = v_uid` cascade-delete. `SettingsScreen`'s delete-account copy (the inline `Account` section text and the confirmation sheet body) mentions the handoff.

**Storage cleanup is server-side, inside `delete_my_account` itself** (`20260717120000_delete_account_server_storage_cleanup.sql`), not client-side. It used to run in `SettingsScreen`'s `confirm()` before the RPC call — a data-loss bug: (a) an RPC failure after cleanup permanently destroyed other users' photos while every DB row survived, and (b) even on success it wiped storage for capsules the RPC *transfers* rather than deletes, whose media should survive. Can't just run *after* the RPC either — once `delete_my_account` succeeds the auth user/JWT is gone, so a follow-up call would 401. Fix: at the top of the function, before any mutation, it computes the exact `storage_key`/`thumbnail_key`/`alt_storage_key` set for media actually about to be deleted — owned capsules with **no other joined member**, plus (when `p_delete_contributions`) the caller's own contributed media in *any* capsule — and deletes those rows directly from `storage.objects` (`bucket_id = 'capsule-media'`), plus `avatars/<uid>/avatar.jpg`. `SettingsScreen.confirm()` is now just the RPC call — no client-side key collection or `storage.remove()`.

⚠️ Outdated: superseded — see `capsule-lifecycle.md` (Delete capsule): SQL deletes from `storage.objects` are now forbidden; cleanup runs client-side via `my_account_storage_keys` before the RPC.
