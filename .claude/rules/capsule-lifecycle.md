## Owner-Only Capsule Actions

All owner-only, silently no-op/navigate away if not owner — **except Archive**, which any joined member can do:

- **Edit capsule** (`EditCapsuleScreen`) — title, description, unlock date, contribution lock date. Via CapsuleDetail header "Edit" or (owner, pre-unlock) Home's long-press context menu. Blocked once unlocked.
- **Archive/restore — PER-MEMBER, not capsule-global** (`20260711150000_per_member_archive.sql`). Archiving stamps `archived_at` on the caller's own `capsule_members` row; hides the capsule from *that user's* feed only (Home's collapsible "Archived" section), never changes other members' view. `capsules.archived_at` (old capsule-global design, `20260706120000_member_archive_capsule.sql`) is retired — frozen for old builds, nothing current reads/writes it. <!-- The old global design was a production bug: any member archiving removed the capsule from every member's Home feed ("capsules keep disappearing" reports). --> RPC **`set_capsule_archived(p_capsule_id, p_archived)`** kept its name/signature but now updates the caller's member row (`security definer`, requires `joined_at is not null`, raises otherwise). `CapsuleDetailScreen` gates the button on `canArchive = myMember?.joined_at != null`, reads state from `myMember.archived_at`; `HomeScreen`'s query selects the member row's `archived_at` alongside the `capsules(...)` embed, merging it onto each card so `capsules`/`archivedCapsules` split on the user's own flag. `EditCapsuleScreen.handleArchive` also routes through the RPC (toasts on failure). Reversible, its own section separate from Danger Zone (Delete-only, `isOwner`-gated). `CapsuleDetailScreen`'s button uses `navigation.goBack()` (not `navigation.reset`) and shows a toast with an **Undo** action (`toast.show(message, { label, onPress })`) that re-calls the RPC in reverse.
- **Home long-press context menu** — opens an Open/Edit/Archive sheet (`HomeScreen`'s `menuCapsule` state) on any card, not just the owner's. Edit only for owner pre-unlock (mirrors `EditCapsuleScreen`'s gate); Archive unconditional since every listed capsule already satisfies `canArchive`. No Undo toast here (unlike CapsuleDetail's) — plain success/failure toast.
- **Delete capsule** — via the **`delete_capsule_with_storage(p_capsule_id)`** RPC (`security definer`, `20260718090000_delete_capsule_with_storage.sql`), not a client-side key-collection + `capsules.delete()` sequence. The old client path selected `storage_key`/`thumbnail_key`/`alt_storage_key` from `media` before deleting the capsule row, but the `media` SELECT policy hides rows from the owner while locked in surprise mode (default), so the select silently returned zero rows and every file was orphaned in the bucket forever (BUGS.md #1). The RPC authorizes inline (`owner_id is distinct from auth.uid()`, null-safe, same pattern as `set_default_superlatives`), collects storage keys as `security definer` (bypasses RLS, sees rows regardless of lock state), then deletes the capsule row (cascades to members, media, reactions, notifications, superlative_categories).

  ⚠️ **The RPC must NOT delete from `storage.objects` directly.** Supabase's `storage.protect_delete()` (statement-level BEFORE DELETE trigger) raises `42501: Direct deletion from storage tables is not allowed. Use the Storage API instead.` Both this RPC and `delete_my_account` did exactly that, breaking capsule and account deletion entirely until `20260726231008`/`20260726231047`. (A row delete never removed the underlying S3 object anyway — that asymmetry is why the guard exists.) Cleanup now runs **client-side, and BEFORE the row delete** — client-side because only the Storage API removes blobs; before, because the delete policy is "you own the capsule," a check that can't pass once the capsule row is gone. `capsule_storage_keys(p_capsule_id)` (definer, owner-authorized) supplies the key list instead of a client-side select. Storage removal is best-effort (orphaned blobs are a cost problem; a capsule that won't delete is user-facing). `delete_my_account` follows the same shape via `my_account_storage_keys(p_delete_contributions)`, which must run before the RPC since that destroys the auth user and the JWT dies with it.

  Storage DELETE policies (`20260726234500`): **`capsule-media` — capsule owner only** (not extended to uploaders, to avoid stranding a media row pointing at a removed blob); **`avatars` — own folder only**.

  ⚠️ **`superlative_winners`'s target FKs are `ON DELETE CASCADE` and must stay that way.** Same XOR check as `superlative_votes` (`(target_user_id IS NOT NULL)::int + (target_media_id IS NOT NULL)::int = 1`) makes `SET NULL` unsatisfiable — nulling either column sums to 0 and raises 23514, aborting the delete. Both `target_user_id` and `target_media_id` had this defect (fixed `20260726231158`); presented as an *unlocked*-capsule-only bug since winners only exist after `finalize_capsule_superlatives`. Confirmation via `<ConfirmModal>` (not `Alert.alert`, no-ops on web). Available from EditCapsule and CapsuleDetail Danger Zone. Owner-only.
- **Manage members** (`ManageMembersScreen`) — lists joined + pending members. Trash icon removes after confirmation. Via CapsuleDetail members section "Manage" button.

## Unlock Cron (`supabase/functions/unlock-capsules`)

Marks `status = 'active'` capsules with `unlock_at <= now()` as `'unlocked'` and pushes to all joined members. Only acts on `unlock_mode = 'time'` capsules — `proximity`/`both` unlock via the `check_in` RPC (see Proximity Unlock).

- **Trigger:** `pg_cron` job `unlock-capsules` runs `* * * * *`, EXISTS-gated (`20260709130000_cron_exists_gates.sql`) — `net.http_post` (and the cold start) only fires when `exists (select 1 from capsules where status='active' and unlock_mode='time' and unlock_at <= now() + interval '24 hours')`. The 24h window covers both an unlock and the widest (1-day) reminder tier below, so no productive tick is skipped — pure invocation-count optimization (~43K/month → near zero at idle). Same pattern on `create-group-capsules` (gated on `groups.next_capsule_at <= now() and recurrence_paused_at is null` — the pause filter was added in `20260717190000_group_cron_gate_pause_filter.sql` after a paused-and-overdue group made the gate permanently true) and the `send-superlative-pushes` POST inside `close-superlative-windows` (gated on unpushed superlative notifications existing — evaluated after that tick's `dispatch_superlative_closing_soon()`/`close_superlative_windows()` calls, unconditional since they're cheap in-database SQL). Re-registering a cron job to change its command: `select cron.unschedule(name)` then `select cron.schedule(name, schedule, command)`.
- **Countdown reminders:** the same function fires pre-unlock pushes at three tiers — **1 day / 1 hour / 10 minutes** before `unlock_at` (`dispatchReminders`, every tick). Each tier does an atomic `update({ <tier>_sent_at: now }).is(<tier>_sent_at, null).gt('unlock_at', now).lte('unlock_at', now + tier).select()` — claims+stamps in one statement so a tier sends at most once (race-safe). Stamp columns: `capsules.unlock_reminder_{1d,1h,10m}_sent_at` (`20260616000000_unlock_reminders.sql`). Inserts durable `unlock_reminder` rows (`pushed_at` set inline) with body from actual remaining time (`formatRemaining`). **Tier windows overlap** (each is `unlock_at <= now() + tier.ms`) — a capsule created shortly before unlock is claimed by all three tiers in one tick; `dispatchReminders` dedupes per capsule across tiers (a `remindedThisRun` Set) to emit at most one reminder per capsule per run (stamps still all commit; normal-lead capsules still get separate 1d/1h/10m reminders on different ticks). Same fix applied to `contribution-nudges`. `time`-mode only. Client renders `unlock_reminder` in `NotificationsScreen` (hourglass icon, capsule-nav).
- **Auth:** `Authorization: Bearer <CRON_SECRET>` via **`requireCronSecret(req)`** (`supabase/functions/_shared/cronAuth.ts`) — the single shared helper used by all six cron functions (`unlock-capsules`, `contribution-nudges`, `dispatch-contribution-activity`, `dispatch-capsule-start`, `send-superlative-pushes`, `report-digest`). Matching value stored in Supabase Vault as `cron_unlock_capsules_secret`, read via `(select decrypted_secret from vault.decrypted_secrets where name = 'cron_unlock_capsules_secret')`.

  ⚠️ **It FAILS CLOSED and must keep doing so.** Each function used to inline `if (CRON_SECRET && auth !== \`Bearer ${CRON_SECRET}\`)`, which was fail-**open**: an unset env var short-circuits the check, and — since these deploy `verify_jwt = false` — the function becomes a fully public unauthenticated endpoint (mass push spam, Expo quota burn). Fixed 2026-07-29 (audit M-1, CWE-636): an unset secret now returns **500 "Server misconfigured"**, and the comparison is constant-time. **Never reintroduce the `SECRET && ...` guard shape** — an unset secret must reject, never bypass.

  **Deploy ordering:** `CRON_SECRET` must already be set before deploying any of these, or all six 500 simultaneously.

  **`create-group-capsules` deliberately does NOT use this helper** — it already fails closed through the `check_cron_secret` Vault RPC (`isAuthorized`, returns false with no token). Two auth styles coexist on purpose.

  **Multi-file deploys:** importing `../_shared/cronAuth.ts` requires the nested layout — `entrypoint_path: "<fn>/index.ts"` plus files `"<fn>/index.ts"` and `"_shared/cronAuth.ts"`. A flat single-file deploy boot-crashes. Verify by POSTing a deliberately wrong bearer: **401 = healthy**, **500 = broken**.
- **`CRON_SECRET` is a project-wide Edge Function secret, not per-function** — set once in Dashboard → Functions → Secrets, every function reads it via `Deno.env.get('CRON_SECRET')` immediately with no per-function step.
- **Idempotency:** the `.eq('status', 'active')` filter means repeat calls within a minute don't re-unlock/re-notify. The in-memory `lastCallTime` rate-limit is dead code on edge runtimes (doesn't survive cold starts) but harmless since the work is idempotent.
- **Rotating the secret:** update Vault (`select vault.update_secret(secret_id, new_value)`) AND the project's Functions → Secrets (project-wide, order doesn't matter for safety). A redeploy is needed per function to pick up the new value (module-load env; deploying the same code via `mcp__supabase__deploy_edge_function` works).

## Instant Unlock (`claim_capsule_unlock`)

The cron flips `status` **up to 60s after `unlock_at`** — the largest part of perceived unlock latency. `claim_capsule_unlock(p_capsule_id)` (`20260801170000_instant_unlock.sql`, `security definer`) lets a joined member's own client flip it the moment it's due. `CapsuleDetailScreen`'s unlock poll calls it instead of re-reading, and reveals off the RPC's returned status.

- **Cannot open anything early.** The UPDATE is guarded by `unlock_at <= now()` evaluated on the **server** clock, so a tampered device clock buys nothing. `security definer` because the `capsules` UPDATE policy is owner-only but any joined member should trigger it (same reasoning as `check_in`). Verified on prod: a real joined member against a not-due capsule returns `active` and changes nothing; a non-member is rejected with `Not a member of this capsule`.
- **`unlock_mode = 'time'` only.** A `both` capsule additionally needs everyone physically together (`check_in`'s half of the contract); flipping it on the date alone would skip that entirely.
- ⚠️ **The unlock push had to be decoupled from the flip.** `unlock-capsules` derived its push list from its own `update … .eq('status','active')`; once a client can win that race, the update matches zero rows and nobody gets the push. The notifier now claims independently via **`capsules.unlock_notified_at`** (`update … .eq('status','unlocked').is('unlock_notified_at', null)` — claim-and-stamp, race-safe against both a concurrent cron tick and a client flip, same shape as `contribution_start_notified_at`). The migration **backfills every already-unlocked capsule** (else the next tick would blast the whole history).
- ⚠️ **The cron's EXISTS gate had to widen too** — now also matches `status='unlocked' and unlock_mode='time' and unlock_notified_at is null` (else a client-flipped capsule never invokes the notifier).
- Notify claim is scoped to `unlock_mode='time'`. **Known gap: proximity/`both` capsules notify nobody on unlock** — `check_in` flips status and inserts no notifications.
- The `capsules_stamp_unlock_meta` BEFORE UPDATE trigger fires on this flip like any other, stamping `unlocked_at`/`superlative_voting_closes_at` identically regardless of path.

**Media genuinely cannot be preloaded before unlock** — the `media` SELECT policy hides rows pre-unlock under surprise mode (default), so there are no `storage_key`s to sign (deliberate, see "Surprise Mode"). `fetchPhotos` fires `Image.prefetch()` on the first `GRID_PREFETCH_COUNT` (12) thumbnails the instant signed URLs land, overlapping the reveal animation. Don't relax RLS to prefetch earlier without an explicit product decision.

## Proximity Unlock

`unlock_mode` (`time`/`proximity`/`both`):
- `time` — unlocks on `unlock_at` via the cron.
- `proximity` — unlocks when all joined members are physically together.
- `both` — date passed **and** together.

**`check_in(p_capsule_id, p_lat, p_lng)` RPC** (`SECURITY DEFINER`) — records location on the caller's `capsule_members` row (`checkin_lat/lng/at`), unlocks if every joined member checked in within the last 10 minutes and the max pairwise distance is `<= proximity_radius_m` (default 100m). `SECURITY DEFINER` so any joined member (not just owner) can trigger; authorizes inline. Returns `{ unlocked, checked_in, total, within_range }`. Distance via `_haversine_m`.

**Check-in UI** — `CheckInCard` (`CapsuleDetailScreen`) renders for locked `proximity`/`both` in place of/alongside `CountdownRing` (proximity hides the ring; `both` shows both). "We're here — check in" requests foreground location (`expo-location`), calls `supabase.rpc('check_in', …)`, shows `N of M here`. Once checked in, flips to a confirmed outlined "✓ You're checked in" state (still tappable to re-check-in — check-ins expire after 10 min and everyone must be in range at once). This `iCheckedIn` state is seeded from the caller's own `capsule_members.checkin_at` — the members query selects it and `MemberRow` carries it — but only if within `CHECKIN_WINDOW_MS` (10 min), so it survives nav away/back yet a stale check-in doesn't falsely show active. The realtime channel fires the reveal for everyone when the last check-in flips `status` to `unlocked`.

**Unlock-mode picker** — `CreateScreen`/`EditCapsuleScreen` "Unlock When" selector (Date/Together/Both). Proximity hides the unlock-date field and skips its validation; `unlock_at` still gets a placeholder (`not null` column, unused for proximity).

## Surprise Mode (`capsules.owner_preview_locked`)

When `owner_preview_locked = true`, **the owner is locked out of viewing media exactly like everyone else** until `status = 'unlocked'` — can still upload, see the member list, and a "N memories waiting" count, but no thumbnails/viewer.

- **Default ON for new capsules** (`default true`). Migration `20260618000000_owner_preview_lock.sql` backfilled pre-existing capsules to `false` (old preview behavior preserved for them).
- **Creation-only.** `CreateScreen`'s "Keep it a surprise" `Switch` (default on) sets the column at insert. No toggle in `EditCapsuleScreen` — by design, so an owner can't flip it off right before unlock to peek (the DB owner-UPDATE policy still technically allows changing it; the client just never exposes a control).
- **Server-side (RLS).** The `media` SELECT policy gates pre-unlock reads on `cm.role in ('owner','contributor') AND NOT c.owner_preview_locked` — the owner genuinely can't obtain `storage_key`s while locked. ⚠️ That policy's membership test was `cm.user_id = auth.uid()` with **no `joined_at is not null` filter**, so an invited-but-never-accepted user could read every media row (captions, uploader ids, storage keys) — despite `20260722120000`'s comment claiming it mirrors the media table's own policy exactly (the *storage* policy did check `joined_at`; this one didn't). Fixed in `20260802120000`. **A membership test anywhere in this codebase means `joined_at is not null`** — `capsule_media_count`, `tally_superlatives`, `set_capsule_archived` all filter on it.
- **Count via SECURITY DEFINER RPC** `capsule_media_count(p_capsule_id)` (joined-member-authorized, 0 for non-members), since RLS hides the rows. `CapsuleDetailScreen.fetchPhotos` calls it only when the media row-read returns zero rows (the ambiguous case); otherwise `mediaCount` is set directly from the fetched row count. The locked box renders `mediaCount`, not `photos.length` (empty under the lock).
- **Client gate:** `canSeePhotos = !isLocked || (isOwner && !capsule.owner_preview_locked)`.

## Capsule Start Date

Optional `contribution_start_at` — the mirror image of `contribution_lock_at`: **nobody, owner included** (deliberately unlike the lock's owner exemption), can add photos until it arrives. For planning a capsule ahead of an event that hasn't happened yet.

**Schema** (`20260716120000_capsule_start_date.sql`): `capsules.contribution_start_at` + `capsules.contribution_start_notified_at` (both nullable timestamptz), `notifications_type_check` gained `capsule_started`, `create_capsule_with_owner` gained a trailing `p_contribution_start_at timestamptz default null`. Existing callers are unaffected (PostgREST maps `.rpc()` by name). The migration **drops the old 10-arg overload before `create or replace`** — a trailing param changes the signature, so without the drop two overloads would coexist and make the original named-arg call ambiguous (PGRST203). RLS: both the `media` and `storage.objects` INSERT policies check the start gate, no owner exemption (see "Contribution lock… TWO layers").

**Cron + edge function** (`20260716120100_capsule_start_cron.sql` + `supabase/functions/dispatch-capsule-start`) — `* * * * *`, EXISTS-gated, Vault-backed `CRON_SECRET` via the shared `cron_unlock_capsules_secret` (`verify_jwt: false`, own auth check). Atomically claims due capsules (`UPDATE ... contribution_start_notified_at = now() ... where ... is null RETURNING`), inserts one `capsule_started` notification per **joined** member (`pushed_at` set inline), pushes via a local ≤100-chunk `sendExpoPush()`.

**Client:**
- `src/components/DatePicker.tsx` exports `START_DATE_QUICK_OPTIONS` (Tomorrow/This weekend/In 3 days/1 week — near-term, vs. the default `QUICK_OPTIONS` which skew too far out). Used by Create and Edit.
- `CreateScreen` — "Starts" `DatePickerField` (optional, with tooltip), rendered above the fold **unconditionally** (unlike Unlock Date, hidden for `proximity` mode). Validation: start must be before both the unlock date and the uploads deadline. Threaded into the RPC as `p_contribution_start_at`.
- `EditCapsuleScreen` — same field (no tooltip), same ordering validation.
- `CapsuleDetailScreen` — computes `notStartedYet` from `contribution_start_at`; gates `canUpload` for everyone including the owner, renders a "Capsule starts `<date>`" pre-start card (`startsBox`) in place of upload controls.
- `HomeScreen` — `CountdownBadge` gained a pre-start branch: a future `contribution_start_at` shows a "Starts in Nd/Nh" badge (reuses `togetherBadge` style, calendar icon), flips to the unlock countdown once start passes.
- `NotificationsScreen` — renders `capsule_started` (camera-outline icon, accent color, capsule-nav): "`<title>` is open for photos now".

**Shipped to production** (`ezxxvvmesegegkdeniri`) — verified end-to-end: a disposable capsule with a past `contribution_start_at` + two joined members produced exactly 2 `capsule_started` notifications (`pushed_at` set), the dedup stamp landed, a second invocation returned `{"claimed":0,"notified":0}` (idempotent), and fixtures were deleted afterward.
