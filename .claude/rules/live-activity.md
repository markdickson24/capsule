## Live Activity Countdown

A lock-screen / Dynamic Island card that counts down to a capsule's **uploads deadline** (`contribution_lock_at ?? unlock_at`) while it's open for photo contributions, with a tap-to-open camera button. iOS 16.2+ only; free for every tier — there is no gate anywhere in this feature, by design (see "Tier enforcement" for where a future one would go if that ever changes).

**Data model.** `capsules.live_activity_enabled boolean not null default true` — the owner's default for the card. **Every pre-existing capsule was backfilled to `false`** (same reasoning as `owner_preview_locked`'s backfill: a capsule that was already live shouldn't suddenly start appearing on members' lock screens the moment they update). `capsule_members.live_activity_override boolean` — a per-member override, `null` = inherit. Effective value is `effectiveLiveActivityEnabled()` (`src/lib/liveActivityPlan.ts`): `override ?? capsule.live_activity_enabled`.

**The `grant update (live_activity_override) on public.capsule_members to authenticated` in the same migration is mandatory, not incidental.** The July 2026 audit (`20260722120000_audit_rls_hardening.sql`) revoked the table-wide UPDATE grant on `capsule_members` and granted back only `joined_at` — so a brand-new column has **no** UPDATE privilege by default, and a client write to it fails `42501` for the whole statement, not just that column. Any future column added to `capsule_members` or `media` needs the same explicit `grant update (col)` line in its own migration.

**Migration lesson (worth re-reading before touching `create_capsule_with_owner` again):** the RPC gained a 12th trailing parameter (`p_live_activity_enabled boolean default true`). Adding a parameter changes the function's type signature, so the migration **drops the old 11-arg overload before `create or replace`** — otherwise two overloads coexist and PostgREST fails the pre-existing call with `PGRST203` (ambiguous). **A signature-changing drop+recreate also silently resets the function's ACL**: the recreated function is a new object in Postgres's eyes and picks up ambient `PUBLIC`/`anon` EXECUTE, undoing `20260718120000_revoke_anon_rpc_execute.sql`'s explicit revoke — confirmed live (`has_function_privilege('anon', oid, 'EXECUTE')` came back true after the drop+recreate). A same-signature `create or replace` does *not* have this problem (it preserves the ACL) — only a signature change does. Migration `20260724120100_live_activity_reassert_rpc_grants.sql` reasserts the revoke. **Anyone changing an RPC's signature in this codebase must re-run its grants in the same migration**, or repeat this regression.

**Architecture:**
- **`targets/liveactivity/`** — a widget extension target added via **`@bacons/apple-targets`** (`app.json`'s plugins list, `{ appleTeamId: 'XL92P6D5PK' }`), not the official `expo-widgets` (requires SDK 56+; this app is on 54) or any third-party kingstinct-style package. Chosen also because `ios/` is gitignored and regenerated on every prebuild (Expo CNG) — a plugin is the only way a native target survives that. `CapsuleLiveActivity.swift` is the widget's SwiftUI view (lock-screen + Dynamic Island compact/expanded/minimal presentations).
- **`modules/expo-live-activity`** — a local Expo native module (same autolinked-from-`modules/` idiom as `expo-dual-camera`) wrapping `ActivityKit`: `isSupported()`, `start(config)`, `update(capsuleId, photoCount, memberCount)`, `end(capsuleId, immediate)`, `listActive()` (returns capsule ids). JS side (`modules/expo-live-activity/index.ts`) guards `Platform.OS === 'ios'` + try/catch around `requireNativeModule`, degrading to unsupported everywhere else (web, Android, Expo Go pre-prebuild) — gate all UI on `isLiveActivitySupported()`.
- **`CapsuleActivityAttributes.swift` is a single shared file**, canonical at `modules/expo-live-activity/ios/CapsuleActivityAttributes.swift`, **symlinked** (git mode `120000`) into `targets/liveactivity/CapsuleActivityAttributes.swift`. ActivityKit matches a running activity to UI by **concrete type** — two independently-declared but field-identical `ActivityAttributes` structs in different modules do **not** interoperate, they're just two unrelated types that happen to look alike. A drift-guard test (`src/lib/liveActivityAttributes.test.ts`) reads both file paths and asserts byte-identical contents, so a tool that replaces the symlink with a real copy is caught immediately rather than failing silently at runtime months later.

**Two verification gotchas that cost real time on this feature — worth remembering for the next Xcode-adjacent task:**
1. This project's generated Xcode project uses **synchronized file-system groups**, so `grep`ping `project.pbxproj` for a filename (e.g. to confirm the widget target references `CapsuleActivityAttributes.swift`) returns 0 regardless of whether the wiring is actually correct — the grep proves nothing. Verify target membership by **compiling** (an unsigned `xcodebuild` of the affected pod/target) and checking for a "cannot find type in scope" error, not by string-matching the project file.
2. A file-scope Swift helper originally named `accentColor` failed to type-check inside `CapsuleLiveActivity.swift`'s `View` conformance — it's shadowed by SwiftUI's deprecated `View.accentColor(_:) -> some View` instance method, so referencing the file-scope function by that name inside a `View` resolves to the method instead. Renamed to **`colorFromHex`**. If you see a mysterious type mismatch on a helper named `accentColor` inside any SwiftUI `View`, this is why.

**Why there's no server component.** The countdown is rendered by **iOS itself** from the activity's `staleDate` (set to the deadline at `start()`) — once started, a Live Activity needs **zero** updates to keep the countdown itself ticking correctly, including while the device is offline. The only things `update()` ever changes are `photoCount`/`memberCount`, and only while the app is actually running — there is no cron, no edge function, no push-to-start for this feature. **This is not the same claim as "stays correct for the whole window"** — see the ~8h system limit below; a long contribution window outlives what any single activity instance can stay alive for, regardless of `staleDate`.

**Lifecycle — `useLiveActivities(userId)`** (`src/hooks/useLiveActivities.ts`, mounted once in `RootNavigator`). Runs a reconcile pass on mount, on every `userId` change, and on every `AppState` foreground (realtime doesn't fire while backgrounded, same reasoning as `CapsuleDetailScreen`'s unlock reconciliation). A pass: fetches the caller's joined capsules + their own `live_activity_override`, computes `desiredActivities()` (pure, in `src/lib/liveActivityPlan.ts`), diffs against `listActiveLiveActivities()`, and calls `start`/`update`/`end` accordingly.

**"What's running" always comes from the native `Activity.activities` list, never a JS-side mirror** — iOS can dismiss an activity on its own (user swipe, 12h expiry, force-quit), and a JS mirror would drift and then try to update/end something that no longer exists. Signing out is not special-cased: with no `userId`, `desiredActivities()` returns `[]`, so every currently-running activity routes through the normal `toEnd` path — this is what prevents a stale card surviving on a signed-out phone.

A `runningRef` guard prevents two overlapping reconcile passes (e.g. a foreground event landing mid-mount-pass) from both issuing redundant native calls, and a `generationRef` guard additionally stops an *abandoned* pass (one that hit the 30s `withTimeout` and gave up) from resuming after a newer pass has already taken over and writing stale data. **Neither guard is the load-bearing protection against a duplicate activity** — `expo-modules-core` dispatches every `AsyncFunction` on a serial `DispatchQueue` (`AsyncFunctionDefinition.swift`'s `defaultQueue`, not `.concurrent`), and `start()`'s closure contains no `await` before its check-then-act, so the native check-then-act is already atomic against other module calls regardless of what the JS side does. The two JS-side guards are worthwhile belt-and-braces (they skip redundant work and prevent a stale write), but removing them would not reintroduce the duplicate-activity bug on its own — it was never actually reachable given the serial native queue.

**Deep links (`useDeepLinks.ts`):** `capsule://capsule/<id>` → `CapsuleDetail`; `capsule://capsule/<id>/camera` → the Camera tab with `targetCapsuleId` preselected (same param `CameraScreen` already reads for the "+ Add Media → Open Camera" flow). **Neither performs a membership write** — unlike `capsule://join/<id>`, a Live Activity only exists on a device that's already a member, so tapping it is just navigation, not a consent act. Signed-out taps are stashed (`pendingOpenStash`, same idiom as `pendingJoinStash`) and drained after sign-in.

**Client surfaces:** a "Lock screen countdown" `Switch` in `CapsuleDetailScreen` (only rendered while `liveActivitySupported && liveActivityWindowOpen`, i.e. inside the capsule's own contribution window) writes the caller's own `live_activity_override` — the single choke point for the setting, so a future tier gate would go there alone. `CreateScreen`'s "More options" and `EditCapsuleScreen` both expose the owner-level default (`capsules.live_activity_enabled`) as a "Live countdown" toggle.

**Explicit non-goals / known limitations:**
- **No push-to-start.** A card only appears the first time the app runs *during* a capsule's contribution window — there's no way to make one appear on a device that never opens the app in that window. Building it would need an Apple `.p8` push key, an ES256-signing edge function talking to APNs directly (Expo's push service **cannot** send `apns-push-type: liveactivity` — this would be a second, parallel push pipeline, not an extension of the existing `sendExpoPush()` helpers), per-device push-to-start token sync, and iOS 17.2+.
- No home-screen widget (this is Live-Activity-only), no Android (ActivityKit is iOS-only).
- **iOS ends any Live Activity after roughly 8 hours active (up to ~12h if it stays on screen), regardless of `staleDate`.** Since the window usually defaults to creation→unlock, most real windows outlive a single activity instance — the honest claim is "present for up to ~8h at a stretch, re-armed whenever the app is opened," not "present for the whole event." The design still ends up correct: `listActive()` won't report a system-expired activity as running, so the next reconcile pass (mount/foreground) treats the capsule as needing a fresh `start()` and re-arms it. A device that's never reopened during the remainder of the window simply shows no card for that stretch — no crash, no stale countdown, just absence.
- **Editing a capsule's deadline while its card is live does not update the card.** Reconciliation keys purely on capsule id — `listActive()` only returns which capsule ids have a running activity, not what deadline each was started with — so the card keeps whatever deadline it was given at `start()`. Extending the deadline makes the card vanish early (it hits its old `staleDate`); shortening it makes the card show time that no longer exists. A real fix needs `listActive()` to also surface the running deadline so reconcile can detect drift and re-`start()`.
- **`title` and `accentHex` are `ActivityAttributes`, not `ContentState`, and are therefore immutable for the activity's lifetime** — same class of staleness as the deadline limitation above. Renaming a capsule or changing your accent color after a card is live leaves that running card showing the old title/color; only ending and re-starting the activity would pick up the new value, and nothing currently triggers that. Separately: on a cold launch, the mount reconcile pass can run before `ThemeContext` has finished fetching the user's real `accent_color`, so a freshly-started card can bake in the default `#FC6A5B` instead of the user's actual accent — a timing race, not a bug in the reconcile logic itself.
- **`photoCount` refreshes on app foreground and when the upload queue drains** (`useLiveActivities` subscribes to `uploadQueue`'s existing pub/sub and reconciles when its global task list transitions from non-empty to empty) — but it's still not real-time: a *different* member's upload doesn't push to your card, only your own foreground/upload cycles do, which is the accepted cost of having no server component.
- **Turning the toggle ON now starts the activity immediately** (`CapsuleDetailScreen.handleToggleLiveActivity`'s `next === true` branch calls `startLiveActivity` directly, mirroring the OFF branch's `endLiveActivity(capsuleId, true)` exactly) — both directions are instant; neither waits for the next reconcile pass.
- **A rapid double-tap of the member toggle can leave the DB and the on-screen toggle briefly disagreeing** — two in-flight writes can resolve out of order over the network (JS single-threadedness only rules out a same-tick race, not two already-in-flight requests completing in reverse order). A monotonic `liveActivityGenRef` generation guard suppresses the misleading toast/restore on the stale response, but doesn't close the underlying DB-side race — it self-corrects on the next fetch, and the Live Activity itself always ends up following whatever the DB actually holds.
- **Requires a fresh dev/EAS build.** A new native target and native module are invisible to the currently-installed binary and to Expo Go. The `CapsuleLiveActivity` widget target needs its own provisioning profile registered in `eas credentials` — its name must never collide with `Capsule` (the main app target) or `CapsuleShare` (the share extension); a past collision on the latter made EAS/fastlane sign the main app with the wrong provisioning profile and broke the build (see "Share Intent").
- **`NSSupportsLiveActivities: true` in `app.json`'s `ios.infoPlist` is required.** Without it, `ActivityAuthorizationInfo().areActivitiesEnabled` is false regardless of the OS version or the user's own Live Activities setting, so `isSupported()` returns false and the entire feature — toggle, card, everything — silently vanishes with no error anywhere. There is no runtime warning for this; if the feature seems to have stopped working entirely, check this key first.
- **`Text(timerInterval:)` must use `windowStart...deadline`, never `Date()...deadline`.** Swift's `...` range operator preconditions `lowerBound <= upperBound` and **traps** (crashes the widget extension) if violated — and ActivityKit re-invokes the view at exactly `staleDate == deadline`, the moment `Date() >= deadline` becomes true, so a live-`Date()` lower bound crashes deterministically at the end of every capsule's window. Always anchor the range at the attribute-level `windowStart`, which is guaranteed `< deadline` by `desiredActivities`.
