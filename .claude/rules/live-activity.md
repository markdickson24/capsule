## Live Activity Countdown

Lock-screen/Dynamic Island card counting down to a capsule's **uploads deadline** (`contribution_lock_at ?? unlock_at`) while it's open for contributions, with a tap-to-open camera button. iOS 16.2+ only; free for every tier — no gate anywhere in this feature, by design.

**Data model.** `capsules.live_activity_enabled boolean not null default true` — the owner's default. **Every pre-existing capsule was backfilled to `false`** (same reasoning as `owner_preview_locked`'s backfill — a capsule that was already live shouldn't suddenly start appearing on members' lock screens after an update). `capsule_members.live_activity_override boolean` — per-member override, `null` = inherit. Effective value: `effectiveLiveActivityEnabled()` (`src/lib/liveActivityPlan.ts`): `override ?? capsule.live_activity_enabled`.

⚠️ **The `grant update (live_activity_override) on public.capsule_members to authenticated` in the same migration is mandatory, not incidental.** The July 2026 audit (`20260722120000_audit_rls_hardening.sql`) revoked the table-wide UPDATE grant on `capsule_members`, granting back only `joined_at` — a brand-new column has **no** UPDATE privilege by default, and a client write fails `42501` for the whole statement. Any future column added to `capsule_members` or `media` needs the same explicit `grant update (col)`.

⚠️ **Migration lesson for `create_capsule_with_owner`:** the RPC gained a 12th trailing param (`p_live_activity_enabled boolean default true`). Adding a parameter changes the signature, so the migration **drops the old 11-arg overload before `create or replace`** — else two overloads coexist and PostgREST fails the pre-existing call with `PGRST203`. **A signature-changing drop+recreate also silently resets the function's ACL** — the recreated function is a new object and picks up ambient `PUBLIC`/`anon` EXECUTE, undoing `20260718120000_revoke_anon_rpc_execute.sql`'s revoke (confirmed live via `has_function_privilege('anon', oid, 'EXECUTE')`). A same-signature `create or replace` doesn't have this problem. `20260724120100_live_activity_reassert_rpc_grants.sql` reasserts the revoke. **Anyone changing an RPC's signature here must re-run its grants in the same migration.**

**Architecture:**
- **`targets/liveactivity/`** — widget extension target added via **`@bacons/apple-targets`** (`app.json` plugins, `{ appleTeamId: 'XL92P6D5PK' }`), not the official `expo-widgets` (needs SDK 56+; app is on 54) or any third-party package — also because `ios/` is gitignored/regenerated on every prebuild (Expo CNG), so a plugin is the only way a native target survives that. `CapsuleLiveActivity.swift` is the widget's SwiftUI view (lock-screen + Dynamic Island compact/expanded/minimal).
- **`modules/expo-live-activity`** — local Expo native module (same autolinked-from-`modules/` idiom as `expo-dual-camera`) wrapping `ActivityKit`: `isSupported()`, `start(config)`, `update(capsuleId, photoCount, memberCount)`, `end(capsuleId, immediate)`, `listActive()` (returns capsule ids). JS side (`modules/expo-live-activity/index.ts`) guards `Platform.OS === 'ios'` + try/catch around `requireNativeModule`, degrading to unsupported everywhere else (web, Android, Expo Go pre-prebuild) — gate all UI on `isLiveActivitySupported()`.
- **`CapsuleActivityAttributes.swift` is a single shared file**, canonical at `modules/expo-live-activity/ios/CapsuleActivityAttributes.swift`, **symlinked** (git mode `120000`) into `targets/liveactivity/CapsuleActivityAttributes.swift`. ActivityKit matches a running activity to UI by **concrete type** — two independently-declared but field-identical `ActivityAttributes` structs do **not** interoperate. A drift-guard test (`src/lib/liveActivityAttributes.test.ts`) reads both file paths and asserts byte-identical contents, so a tool that replaces the symlink with a real copy is caught immediately.

**Two Xcode-adjacent gotchas:**
1. This project's generated Xcode project uses **synchronized file-system groups**, so `grep`ping `project.pbxproj` for a filename proves nothing about whether wiring is correct. Verify target membership by **compiling** (an unsigned `xcodebuild` of the affected pod/target) and checking for a "cannot find type in scope" error.
2. A file-scope Swift helper originally named `accentColor` failed to type-check inside `CapsuleLiveActivity.swift`'s `View` conformance — shadowed by SwiftUI's deprecated `View.accentColor(_:) -> some View` instance method. Renamed to **`colorFromHex`**. A mysterious type mismatch on a helper named `accentColor` inside any SwiftUI `View`: this is why.

**Why there's no server component.** The countdown is rendered by **iOS itself** from the activity's `staleDate` (set to the deadline at `start()`) — once started, a Live Activity needs **zero** updates to keep the countdown ticking correctly, including offline. `update()` only ever changes `photoCount`/`memberCount`, and only while the app is running — no cron, no edge function, no push-to-start. **Not the same claim as "stays correct for the whole window"** — see the ~8h system limit below.

**Lifecycle — `useLiveActivities(userId)`** (`src/hooks/useLiveActivities.ts`, mounted once in `RootNavigator`). Runs a reconcile pass on mount, on every `userId` change, and on every `AppState` foreground (realtime doesn't fire while backgrounded). A pass: fetches the caller's joined capsules + their own `live_activity_override`, computes `desiredActivities()` (pure, `src/lib/liveActivityPlan.ts`), diffs against `listActiveLiveActivities()`, calls `start`/`update`/`end` accordingly.

**"What's running" always comes from the native `Activity.activities` list, never a JS-side mirror** — iOS can dismiss an activity on its own (user swipe, 12h expiry, force-quit), and a JS mirror would drift and try to update/end something that no longer exists. Signing out isn't special-cased: with no `userId`, `desiredActivities()` returns `[]`, so every running activity routes through the normal `toEnd` path — this prevents a stale card surviving on a signed-out phone.

A `runningRef` guard prevents two overlapping reconcile passes; a `generationRef` guard stops an *abandoned* pass (one that hit the 30s `withTimeout` and gave up) from resuming after a newer pass has taken over. **Neither guard is the load-bearing protection against a duplicate activity** — `expo-modules-core` dispatches every `AsyncFunction` on a serial `DispatchQueue` (`AsyncFunctionDefinition.swift`'s `defaultQueue`, not `.concurrent`), and `start()`'s closure has no `await` before its check-then-act, so the native check-then-act is already atomic regardless of the JS side. The JS guards skip redundant work and prevent a stale write but aren't what prevents duplicates.

**Deep links (`useDeepLinks.ts`):** `capsule://capsule/<id>` → `CapsuleDetail`; `capsule://capsule/<id>/camera` → the Camera tab with `targetCapsuleId` preselected (same param `CameraScreen` already reads for "+ Add Media → Open Camera"). **Neither performs a membership write** — unlike `capsule://join/<id>`, a Live Activity only exists on a device already a member, so tapping is just navigation. Signed-out taps are stashed (`pendingOpenStash`, same idiom as `pendingJoinStash`) and drained after sign-in.

**Client surfaces:** a "Lock screen countdown" `Switch` in `CapsuleDetailScreen` (only rendered while `liveActivitySupported && liveActivityWindowOpen`) writes the caller's own `live_activity_override` — the single choke point for the setting, so a future tier gate would go there alone. `CreateScreen`'s "More options" and `EditCapsuleScreen` both expose the owner-level default (`capsules.live_activity_enabled`) as a "Live countdown" toggle.

**Explicit non-goals / known limitations:**
- **No push-to-start.** A card only appears the first time the app runs *during* a capsule's contribution window. Building it would need an Apple `.p8` push key, an ES256-signing edge function talking to APNs directly (Expo's push service **cannot** send `apns-push-type: liveactivity` — this would be a second, parallel push pipeline, not an extension of the existing `sendExpoPush()` helpers), per-device push-to-start token sync, and iOS 17.2+.
- No home-screen widget, no Android (ActivityKit is iOS-only).
- **iOS ends any Live Activity after roughly 8 hours active (up to ~12h if it stays on screen), regardless of `staleDate`.** Most real windows (default creation→unlock) outlive a single instance — honestly "present for up to ~8h at a stretch, re-armed whenever the app is opened," not "present for the whole event." `listActive()` won't report a system-expired activity as running, so the next reconcile pass re-arms it with a fresh `start()`. A device never reopened during the remainder simply shows no card for that stretch — no crash, just absence.
- **Editing a capsule's deadline while its card is live does not update the card.** Reconciliation keys purely on capsule id — `listActive()` only returns which ids have a running activity, not what deadline each was started with — so the card keeps whatever deadline it got at `start()`. Extending the deadline makes the card vanish early; shortening it makes it show time that no longer exists. A real fix needs `listActive()` to also surface the running deadline so reconcile can detect drift and re-`start()`.
- **`title` and `accentHex` are `ActivityAttributes`, not `ContentState`, and are therefore immutable for the activity's lifetime** — same class of staleness as above. Renaming a capsule or changing accent color after a card is live leaves it showing the old value; only ending and re-starting picks up the new one, and nothing currently triggers that. Separately: on a cold launch, the mount reconcile pass can run before `ThemeContext` has finished fetching the real `accent_color`, so a freshly-started card can bake in the default `#FC6A5B` instead — a timing race, not a bug in the reconcile logic.
- **`photoCount` refreshes on app foreground and when the upload queue drains** (`useLiveActivities` subscribes to `uploadQueue`'s pub/sub, reconciles on a non-empty→empty transition) — still not real-time: a *different* member's upload doesn't push to your card.
- **Turning the toggle ON now starts the activity immediately** (`CapsuleDetailScreen.handleToggleLiveActivity`'s `next === true` branch calls `startLiveActivity` directly, mirroring the OFF branch's `endLiveActivity(capsuleId, true)`) — both directions instant, neither waits for the next reconcile pass.
- **A rapid double-tap of the member toggle can leave the DB and the on-screen toggle briefly disagreeing** — two in-flight writes can resolve out of order over the network. A monotonic `liveActivityGenRef` generation guard suppresses the misleading toast/restore on the stale response but doesn't close the underlying DB-side race — it self-corrects on the next fetch, and the Live Activity itself always ends up following the DB.
- **Requires a fresh dev/EAS build.** A new native target/module is invisible to the currently-installed binary and to Expo Go. The `CapsuleLiveActivity` widget target needs its own provisioning profile registered in `eas credentials` — its name must never collide with `Capsule` (main app target) or `CapsuleShare` (share extension); a past collision on the latter made EAS/fastlane sign the main app with the wrong provisioning profile and broke the build (see "Share Intent").
- **`NSSupportsLiveActivities: true` in `app.json`'s `ios.infoPlist` is required.** Without it, `ActivityAuthorizationInfo().areActivitiesEnabled` is false regardless of OS version or the user's own setting, so `isSupported()` returns false and the entire feature — toggle, card, everything — silently vanishes with no error anywhere. Check this key first if the feature seems to have stopped working entirely.
- **`Text(timerInterval:)` must use `windowStart...deadline`, never `Date()...deadline`.** Swift's `...` range operator preconditions `lowerBound <= upperBound` and **traps** (crashes the widget extension) if violated — and ActivityKit re-invokes the view at exactly `staleDate == deadline`, the moment `Date() >= deadline` becomes true, so a live-`Date()` lower bound crashes deterministically at the end of every capsule's window. Always anchor the range at the attribute-level `windowStart`, guaranteed `< deadline` by `desiredActivities`.
